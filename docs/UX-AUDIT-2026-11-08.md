# 发布前用户体验审计 — 2026-11-08

> 触发：用户要求做一次「发布前 UX 审计」，重点是**会把用户劝退**的问题：
> 错误提示、卡住说不通的流程（"牢定的问题"）、以及各类 bug。
>
> 方法：静态扫描（中英文文案、原生对话框、静默失败路径）+ 真实浏览器逐屏截图
> （1440 / 375）+ 全量端到端回归。本文只记录**已修**与**已知但不修**，不写计划。

严重度：**致命** = 新用户第一次打开就会放弃；**高** = 日常使用会踩到并产生不信任；
**中** = 让人皱眉；**低** = 观感。

---

## 1. 致命

### F1 · 首屏是死胡同

没有连接邮箱时，收件箱空态写的是：

> **Inbox 是给你的重要邮件** —— 重要的、需要你来处理的对话会出现在这里。新邮件到了会自动出现在这里。

三处问题：英文标题；"新邮件会自动出现"是**假的**（没连账户就永远不会到）；
没有任何按钮 —— 唯一入口是顶栏那个没有文字的胶囊。

**修**：`还没有连接邮箱 / 连接你的第一个邮箱后，新邮件会自动收进这里` + 主按钮
「添加邮箱账户」直达 设置 → 账户。已连接但没邮件时退回到安静的
「收件箱是空的」。`e2e/first-run.spec.ts` 锁住。

### F2 · 「便签」在桌面 App 里完全没有反应

`window.prompt("写一条便签…")` —— WKWebView 不实现 JS 文本输入面板（宿主不接就
永远返回 null）。也就是说 macOS / iOS 上点便签什么都不发生，且**没有任何提示**。

**修**：应用内 Modal（textarea + 贴上/取消），`data-sticky-input` 便于测试。

## 2. 高

### F3 · 删除任务用 `window.confirm`

同样的原生面板问题：确认框在 WKWebView 里不可靠，且不可样式化、会阻塞。
**修**：`ConfirmDialog`（全站其它破坏性操作早已在用它）。

### F4 · 计数越用越错，还会吞掉真实邮件

`usePaginatedMessages.removeByIds` 在 `setPages(next)` **之后**又读了一次 `pages()`。
Solid 信号是同步的，所以那个减法恒为 0：

- 归档 / 删除 / 标已读之后，列表头部的「N 总数」只增不减（截图里 4 封邮件显示「5 总数」、
  tab 显示 3 而列表只有 2 行）；
- 更糟的是 `offset` 也没退回：100 行里移除 1 行后 `loadMore` 从 100 开始取，
  **跳过**了滑到 99 号位的那封邮件 —— 那封信永远不会出现。

**修**：写入前快照数组，总数与 offset 都按真实移除数递减。3 条单测覆盖
（总数、offset/loadMore、未加载的 id）。

### F5 · 读一封信后，头部和徽章不跟着变

列表在内存里把消息从一个 tab 挪到另一个 tab，但「最近 30 天 N 封待读」、账户 tab
上的计数、侧栏未读徽章都是 SQL 计数，只在 tick 时刷新。结果就是「3 封待读」下面
摆着 2 行。

**修**：读信 / 切换已读后主动刷新这些计数。

### F6 · 顶栏账户徽章是陈旧的

`SyncBadge` 的账户列表只读一次，之后不再订阅任何刷新：明明已经连了两个邮箱，
徽章还写着「添加邮箱账户 →」。同时每次刷新都会闪一下「加载中…」。

**修**：跟随 soft tick 重取；「加载中…」只在首次无数据时出现。

### F7 · 错误 toast 会永久堆叠、无上限、不去重

错误 toast 设计上不自动消失（合理：没看到的失败没法处理）。但既没有去重也没有
上限 —— 后台同步/提取循环一旦持续失败，每分钟新增一条永久卡片，最终糊满整个界面，
比不提示更糟。

**修**：同 `kind` + 同文案合并为一条并显示 ×N；队列上限 4 条，丢最旧的、保留最新的。
4 条单测覆盖。

## 3. 中

### F8 · 中英混排

一个中文产品里散落着英文 chrome：

| 位置 | 原文 |
|---|---|
| 通知面板 | Notifications / Mark all read / Today / Yesterday / Earlier / aria "Close" |
| 任务面板 | 标题 Task；字段 Status / Priority / Due / Notes；选项 Todo / Doing / Done / Low / Normal / High |
| 全局搜索 | Results for “…” / Type to search… ⏎ select · ↑↓ navigate · Esc close；分组 People / Messages / Files / Events |
| 任务页 | H1 "Tasks"（侧栏写的是「任务」） |
| 筛选台 | 分桶按钮 Inbox / Stream / Records（侧栏是 收件箱 / 报刊 / 单据）；历史页标题 "Gate 历史" |
| 报刊空态 | "Stream 是空的" |
| 归档提示 | 「已归档到 Records」「移回 Inbox」「仍保留在 Stream 中」 |
| 收件箱 tablist | aria-label "Inbox sections" |

**修**：全部改中文；保留 HEY 品牌词时一律写成「English（中文）」的成对形式。

### F9 · 375px 下邮件头部被裁

「富文本 / 纯文本 / 源码」三段控件在手机上超出右边界，`源码` 被切掉。该控件本来
有窄屏 dropdown 形态，但判断依赖 `ResizeObserver` 的**尺寸变化**回调；面板挂载时
就已经是手机宽度，那次回调可能拿不到值，于是永远停在宽屏形态。

**修**：断点也参与判断（`panelNarrow() || isMobile()`）。

## 7. 第二轮（同日补充）

第一轮之后又逐屏过了一遍日历 / 联系人 / 文件 / 冷启动，并扫了一遍 Rust 的 panic 面。

### F14 · 一条没有颜色的日程会把整个日历打成错误页（致命）

`textColorForBg(e.color)` → `hexToRgb` → `hex.replace(...)`，遇到 `color` 缺失就抛
`Cannot read properties of undefined (reading 'replace')`。日视图、周视图、月视图、
议程四个入口都走这个函数 —— **只要有一行日程没有颜色，整个月视图就变成错误页**。

颜色在实际数据里可以是空的（导入的邀请、早期写入的行），所以现在把缺失/空值当作
「没有颜色」，回落到可读的 ink token。`e2e/error-surface.spec.ts` 专门种了一条
无颜色日程并断言日历正常渲染；去掉修复后该用例失败。

### F15 · Rust 侧的锁中毒会把整个 App 拖死（高）

`Mutex::lock().unwrap()` 共 8 处（同步状态、通知偏好、vault 缓存、MCP endpoint、
agent 客户端注册表）。只要有一个线程在持锁时 panic，锁就被标记为中毒，
**之后每一次 `lock().unwrap()` 都会继续 panic** —— 后台同步里的一次 panic 会顺着
所有 IPC 调用扩散成「整个应用没反应」。

中毒的意思是「上一个持有者死了」，不是「数据不可用」，所以改成
`unwrap_or_else(|e| e.into_inner())` 拿回 guard 继续跑。
