# 发布前用户体验审计 — 2026-11-08

> 触发：用户要求做一次「发布前 UX 审计」，重点是**会把用户劝退**的问题：
> 错误提示、卡住说不通的流程（"牢定的问题"）、以及各类 bug。
>
> 方法：静态扫描（中英文文案、原生对话框、静默失败路径）+ 真实浏览器逐屏截图
> （1440 / 375）+ 全量端到端回归。本文只记录**已修**与**已知但不修**，不写计划。

严重度：**致命** = 新用户第一次打开就会放弃；**高** = 日常使用会踩到并产生不信任；
**中** = 让人皱眉；**低** = 观感。

---

## 1. 致命

### F1 · 首屏是死胡同

没有连接邮箱时，收件箱空态写的是：

> **Inbox 是给你的重要邮件** —— 重要的、需要你来处理的对话会出现在这里。新邮件到了会自动出现在这里。

三处问题：英文标题；"新邮件会自动出现"是**假的**（没连账户就永远不会到）；
没有任何按钮 —— 唯一入口是顶栏那个没有文字的胶囊。

**修**：`还没有连接邮箱 / 连接你的第一个邮箱后，新邮件会自动收进这里` + 主按钮
「添加邮箱账户」直达 设置 → 账户。已连接但没邮件时退回到安静的
「收件箱是空的」。`e2e/first-run.spec.ts` 锁住。

### F2 · 「便签」在桌面 App 里完全没有反应

`window.prompt("写一条便签…")` —— WKWebView 不实现 JS 文本输入面板（宿主不接就
永远返回 null）。也就是说 macOS / iOS 上点便签什么都不发生，且**没有任何提示**。

**修**：应用内 Modal（textarea + 贴上/取消），`data-sticky-input` 便于测试。

## 2. 高

### F3 · 删除任务用 `window.confirm`

同样的原生面板问题：确认框在 WKWebView 里不可靠，且不可样式化、会阻塞。
**修**：`ConfirmDialog`（全站其它破坏性操作早已在用它）。

### F4 · 计数越用越错，还会吞掉真实邮件

`usePaginatedMessages.removeByIds` 在 `setPages(next)` **之后**又读了一次 `pages()`。
Solid 信号是同步的，所以那个减法恒为 0：

- 归档 / 删除 / 标已读之后，列表头部的「N 总数」只增不减（截图里 4 封邮件显示「5 总数」、
  tab 显示 3 而列表只有 2 行）；
- 更糟的是 `offset` 也没退回：100 行里移除 1 行后 `loadMore` 从 100 开始取，
  **跳过**了滑到 99 号位的那封邮件 —— 那封信永远不会出现。

**修**：写入前快照数组，总数与 offset 都按真实移除数递减。3 条单测覆盖
（总数、offset/loadMore、未加载的 id）。

### F5 · 读一封信后，头部和徽章不跟着变

列表在内存里把消息从一个 tab 挪到另一个 tab，但「最近 30 天 N 封待读」、账户 tab
上的计数、侧栏未读徽章都是 SQL 计数，只在 tick 时刷新。结果就是「3 封待读」下面
摆着 2 行。

**修**：读信 / 切换已读后主动刷新这些计数。

### F6 · 顶栏账户徽章是陈旧的

`SyncBadge` 的账户列表只读一次，之后不再订阅任何刷新：明明已经连了两个邮箱，
徽章还写着「添加邮箱账户 →」。同时每次刷新都会闪一下「加载中…」。

**修**：跟随 soft tick 重取；「加载中…」只在首次无数据时出现。

### F7 · 错误 toast 会永久堆叠、无上限、不去重

错误 toast 设计上不自动消失（合理：没看到的失败没法处理）。但既没有去重也没有
上限 —— 后台同步/提取循环一旦持续失败，每分钟新增一条永久卡片，最终糊满整个界面，
比不提示更糟。

**修**：同 `kind` + 同文案合并为一条并显示 ×N；队列上限 4 条，丢最旧的、保留最新的。
4 条单测覆盖。

就已经是手机宽度，那次回调可能拿不到值，于是永远停在宽屏形态。

**修**：断点也参与判断（`panelNarrow() || isMobile()`）。

## 7. 第二轮（同日补充）

第一轮之后又逐屏过了一遍日历 / 联系人 / 文件 / 冷启动，并扫了一遍 Rust 的 panic 面。

### F14 · 一条没有颜色的日程会把整个日历打成错误页（致命）

`textColorForBg(e.color)` → `hexToRgb` → `hex.replace(...)`，遇到 `color` 缺失就抛
`Cannot read properties of undefined (reading 'replace')`。日视图、周视图、月视图、
议程四个入口都走这个函数 —— **只要有一行日程没有颜色，整个月视图就变成错误页**。

颜色在实际数据里可以是空的（导入的邀请、早期写入的行），所以现在把缺失/空值当作
「没有颜色」，回落到可读的 ink token。`e2e/error-surface.spec.ts` 专门种了一条
无颜色日程并断言日历正常渲染；去掉修复后该用例失败。

### F15 · Rust 侧的锁中毒会把整个 App 拖死（高）

`Mutex::lock().unwrap()` 共 8 处（同步状态、通知偏好、vault 缓存、MCP endpoint、
agent 客户端注册表）。只要有一个线程在持锁时 panic，锁就被标记为中毒，
**之后每一次 `lock().unwrap()` 都会继续 panic** —— 后台同步里的一次 panic 会顺着
所有 IPC 调用扩散成「整个应用没反应」。

中毒的意思是「上一个持有者死了」，不是「数据不可用」，所以改成
`unwrap_or_else(|e| e.into_inner())` 拿回 guard 继续跑。

## 10. 性能（发布前）

### 10.1 运行时：没有问题

`e2e/perf-2-pass.spec.ts` 全量跑（1440×900，Chromium）：

| 指标 | 1x 数据（1500 联系人 / 4000 邮件） | 3x 数据（4500 / 12000 / 200 事件） |
|---|---|---|
| 视图挂载 | 38–97 ms（最慢 Files 97 ms） | Insights 124 ms，其余 70–80 ms |
| 滚动帧 | 16.5–16.8 ms 均帧（60 fps） | 16.7 ms 均帧，**0 丢帧** |
| 长任务 | 0 | 0 |
| frame p95 | 17.6–17.7 ms | 17.7 ms（Insights 27.3 ms） |

结论：渲染层没有「大问题」。Insights 在 3x 数据下 p95 27 ms 是唯一偏软的点，翻页与滚动仍然 60 fps。

### 10.2 冷启动：入口包曾占全部的 55%（已修）

第一次 `pnpm build` 的入口 chunk 是 **583 kB / 177 kB gzip** —— 因为所有浮层都在
入口里静态 import：详情面板（连带 7 个面板，MessagePanel 单个 2000 行 + DOMPurify）、
撰写窗口、命令面板（Fuse）、全局搜索、Agent 面板、新手引导。

改为 `lazy()` + 各自可见信号门控后：

| chunk | 改前 | 改后 |
|---|---|---|
| **入口** | 583 kB / 177 kB gz | **265 kB / 87 kB gz**（−55% / −51%） |
| DetailPanel | 在入口内 | 125 kB / 35 kB gz，首次打开时拉 |
| Compose | 在入口内 | 35 kB / 12 kB gz，首次撰写时拉 |
| fuse | 在入口内 | 27 kB / 10 kB gz，首次 ⌘K 时拉 |

preview 构建冷导航：**FCP 108 ms**，首屏 JS 传输约 109 kB。

### 10.3 每次同步都会重拉整张联系人表（已修）

Imbox 的联系人映射（卡片姓名/头像、首次发件人徽标、优先级分数）走的是
`listContacts()` = `SELECT *` + 每行 5 次 `JSON.parse`，并且在**每个 soft sync tick**
重读一次。1500 个联系人时，每次 tick 都要把 notes / pattern / stageHistory / topics
这些重列搬过 IPC —— 与 §11.7 那次 8 GB OOM 是同一个模式，只是烧得慢。

新增 `listContactsForList()`：只取列表真正用到的 7 列，其余字段留空；打开联系人时
详情面板照旧 `getContact(id)` 取全量。单测断言「保留渲染字段 / 丢弃全部重列 /
序列化体积不到全量的三分之一」。

### 10.4 顺带发现：生产构建在浏览器里是坏的（已修）

`getDb()` 只在 `import.meta.env.DEV` 时用内存 MockDb，于是**打包产物**在普通浏览器
里会走 `Database.load`，没有 Tauri 运行时 → `select` 返回 null → 第一个 `.map()` 抛
`Cannot read properties of null (reading 'map')` → 错误边界把整个应用换成
「界面遇到问题」。也就是说 `vite preview` / 任何对外分享的构建看起来都是坏的。
浏览器现在一律走 MockDb（动态 import，Tauri 包不会加载那块）。

### 10.5 仍然已知的性能债

| 项 | 状态 |
|---|---|
| 10 万封压测 | 未做（`docs/TODOS.md` 已有条目）。当前最大真实邮箱 4300 封，3x 合成数据无压力 |
| Insights 3x p95 27 ms | 可接受；若要更快需要预聚合，暂不做 |

## 11. 发布就绪轮（2026-11-09）— 把「不能发布」变成「可以发布」

用户要求把审计出的全部 P0/P1/P2 做完，并以「发布且不劝退」为标准做深度测试。

### 11.1 P0 · 搜索（实测两个硬缺陷）

真实 46 封邮箱上量过：

```
MATCH 'font'      → 3 条     ✅
MATCH '郝亚伟'    → 1 条     （只是因为它是整段的开头）
MATCH '拒付'      → 0 条     ❌ 标题是「郝亚伟先生的拒付资料」
MATCH 'Re: 报价'  → ERROR: no such column: Re
MATCH 'a-b'       → ERROR: no such column: b
```

- `unicode61` 不切分中日韩：整段中文是一个 token；迁移 0032 改用 `trigram` 索引，
  任意 3 字以上子串都能命中。
- 查询原样进 FTS5 语法：`utils/search.ts` 现在逐词加引号，1–2 字的词（「拒付」「发票」）
  走 LIKE 回退（trigram 索引不到 3 字），LIKE 输入做了转义 + `ESCAPE '\'`。
- 顺带修了测试替身：`mock-db` 根本没有 `MATCH` 分支，`WHERE search_index MATCH $1`
  产生零条件 → 返回全表，**此前所有搜索测试都是假绿**。现在支持 MATCH 与 ESCAPE。

### 11.2 P0 · 连接邮箱要真的连一次

以前点「添加并连接」只提示「密码已存入钥匙串」——那是对存储的陈述，不是「邮箱能用」。
现在保存后立刻跑一轮 IMAP，用 `getSyncState().error_code` 分类（`utils/account-verify.ts`）：

| code | 处理 |
|---|---|
| 无 | 成功，提示并开始导入 |
| `auth_failed` / `missing_credentials` | **回滚账户** + 内联报错（带服务商凭据提示） |
| `network` / `sync_failed` | 保留账户，告知会自动重试 |
| 其它未知 | 保留（删掉用户刚输入的邮箱比留着更糟） |

浏览器预览明确写「未验证连接」，不再暗示成功。

### 11.3 P1 · 撰写 / 发送

- **富文本**：textarea 保持不动（contenteditable 要重做选区、撤销、IME、移动端键盘），
  工具条把选区包进极小的 markdown 子集，发送时渲染两次：HTML 收件人拿到
  `<strong>/<em>/<a>/<ul>`，纯文本收件人拿到**去掉标记**的同一段话。
- **撤销发送**：发送先落草稿再延迟 5 秒；撤销会带着正文重开撰写窗口。窗口内退出
  应用也不会丢（草稿状态仍是 edited，不是 sent）。
- **顺带修的真 bug**：`RecipientInput` 只在回车/逗号时把输入变成 pill，**失焦不提交**。
  于是「打好地址直接点发送」时草稿里收件人还是空，发送按钮是禁用的、点了没反应，
  而输入框里明明显示着地址。现在失焦会提交完整地址；发送按钮也不再 `disabled`，
  点它会说明缺什么。

### 11.4 P1 · 列表 / 日历

- **多选**：Stream / Records / Trash / Spam 一直只会提示「多选暂只在 Inbox 可用」。
  现在每行有勾选框（常显、35% 透明度），批量条从 Imbox 抽成全局
  `BulkSelectionBar`，哪个视图产生的选择都用同一套 稍后回复 / 归档 / 删除 / 取消。
- **日历键盘**：←/→ 一天（周视图一周、年视图一月）、↑/↓ 一周、Enter 打开当天第一场；
  输入框和打开的对话框里不抢键。

### 11.5 P1 · 10 万封压测（发现了两个悬崖）

`src-tauri/tests/scale_100k.rs`（`#[ignore]`）建 10 万封真实体量的库并计时：

| 查询 | 修复前 | 修复后 |
|---|---|---|
| 首屏第一页 | 72 ms | **4 ms** |
| 翻到第 500 页（OFFSET 50 000） | **17 272 ms** | keyset **0 ms** |
| 侧栏未读 | — | **6 ms** |
| 30 天未读 | — | **17 ms** |
| 每账户徽章 | — | **12 ms** |
| 中文三字搜索 | — | **506 ms** |
| pile（稍后回复/搁置/提醒） | **705 ms** | **0 ms** |
| 单封详情 | — | **0 ms** |

- OFFSET 分页改成 keyset 游标（`(timeline_at, id) < (?, ?)`），全量走完 10 万封
  **100 000 条不重不漏**。
- pile 的 `OR` 三条件击穿了迁移 0022 的 partial index → 拆成三条窄查询在内存合并。
- 迁移 0033 补 `(bucket, direction, timeline_at DESC)` 与 `(ac, bucket, unread)` 索引。

### 11.6 P2

- **密度**（紧凑/标准/舒适）+ **强调色**（5 个预设，改 `--palm` 系列）：纯 CSS 变量，
  开机与设置里即时生效。密度会同步 `contain-intrinsic-size`，否则虚拟滚动条会跳。
- **打印**：`styles/print.css` 隐藏外壳与浮层、详情面板脱离 `fixed`，⌘P 打印当前这封；
  更多菜单加「打印」。
- **通知声音**：可只留横幅不出声（`notifications.sound` → Rust `.sound("default")`）。
- **筛选台决定沉淀**：卡上勾「以后这个发件人的邮件都这样处理」→ 写 `mail_rules`。
  `upsert_mail_rule` 改为返回规则 id —— `safeInvoke` 成功和失败都返回 null，
  不返回值就无法区分「存好了」和「IPC 被吞了」。
